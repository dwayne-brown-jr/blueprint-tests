## Context Carry
One-liner: FormCoach gives home gym users a weekly strength plan and checks their form from a short phone video.
Roles: member (sees own plans, videos, progress), coach (me, edits plan templates). Members must NEVER see other members' videos or body measurements.
Core loop: member opens today's workout, logs sets, records one 10-second form video, gets feedback.
V1: weekly plan, set logging, form video upload with AI feedback, progress chart, $9.99/month subscription for plans and form checks.
Data: members (email, weight, measurements - sensitive), workouts, sets, videos (private), subscriptions.

## Context Carry (ARCHITECTURE.md)
Platforms: iPhone and Android app-store app. Stack: Expo (React Native) app, Supabase (database, auth, private storage), Supabase Edge Functions for AI form checks and purchase checks, RevenueCat for in-app subscriptions (Apple and Google billing), EAS Build and Submit.
Entities: members, workouts, sets, videos, subscriptions.
Trust boundaries: no secret keys in the app; only the Supabase anon key ships, with RLS on every table; login tokens in expo-secure-store; AI calls and subscription checks on the server; videos in a private bucket with expiring links; role stored in a server-only table.
ADRs: ADR-1 Expo for one codebase; ADR-2 RevenueCat, verified server-side by webhook; ADR-3 Supabase; ADR-4 OpenAI vision via Edge Function with 5 checks per day per member.

## Context Carry (DESIGN.md)
Direction: "Chalk and iron": off-white #F4F1EA background, near-black #151515 text, safety orange #FF5A1F for the one primary action per screen. Display font: Archivo Black; body: IBM Plex Sans 16/24. Big thumb targets (min 48pt), one primary action per screen, no gradients, square 6pt corners.

Write PLAN.md as a sequence of MILESTONES made of SLICES.

Rules for slices:
- Every build prompt must be self-contained. Include the exact values it needs (colors, fonts, field names, rules, acceptance criteria) instead of pointing to a section number, because my builder may only have the short summaries.
- A slice is one working, visible improvement a person can test in under 5 minutes.
- A slice touches as few files as possible and never mixes UI redesign with data changes.
- Order: project skeleton → design tokens & layout shell → data + access rules → core loop end-to-end (ugly is fine) → remaining V1 features → empty/error states → polish → security gate → launch.
- The core loop must work end-to-end by the end of Milestone 2, even if rough.

For each slice:
- [ ] **ID & name**
- Goal (one sentence)
- Build prompt: the exact instruction to paste into the agent, referencing SPEC/ARCHITECTURE/DESIGN sections by number
- How to test: steps a non-developer can follow, and what they should see
- Done when: acceptance criteria copied from the spec

At the top, include a "Definition of Done" that applies to every slice (no console errors, works at mobile width, uses DESIGN.md tokens only, no secrets in frontend code).

If the architecture says this is an iPhone or Android app-store app:
- Replace "works at mobile width" with "works on a real phone, or the phone simulator, at the smallest screen size we support". "No secrets in frontend code" also means none in the app itself.
- In Milestone 1, add a slice that gets the app running on my own phone (for example through Expo Go, TestFlight, or Google Play internal testing), so every later slice is tested on a real phone.
- "How to test" steps say which phone to use and how to get the latest version onto it.
- Before the launch milestone, add slices for: in-app account deletion (Apple requires it for apps that let people create accounts), the store listing (screenshots, description, privacy details), a test account the store reviewer can log in with, and submitting for review. Allow time for review in the plan.
